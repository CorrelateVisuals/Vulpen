**Explained to the lead**
- **B, why 512 nodes.** Pass blocks come from one descriptor pool of `max_passes = 1024` (`Pipelines.cpp`). That number was picked when the pool was written; it is no GPU limit. An edit builds the new schedule while the old one exists, since the old one hands over operators, pipelines and buffers. The new schedule makes a fresh block for every node, so an edit holds 2N blocks at its peak.
  - Proposal: the new schedule takes each unchanged node's block, as it already takes pipelines and buffers. An edit then needs N plus the nodes it changed. That is about 10 lines in `Schedule`, and saves the 8–11% of a replay spent making and freeing blocks.
  - Then either raise the cap, or let `Pipelines` add a pool when one fills, so no cap remains. With no cap, T14's 1,025-pass case goes.
- **C, "a correct script prints errors".** Each edit rebuilds and checks the whole graph (A02). A script that is right as a whole passes through states that are not.
  - Between `node add p1 …` and `connect c1 probe.samples p1.values`, p1 reads nothing, so the rebuild prints `{!!!} view.vlp node p1: values reads nothing: …`. The next line fixes it, and the run exits 0. The 400-probe replay prints 400 such lines.
  - Proposal: rebuild once before the next frame, not after every edit.
    - Measured with a throwaway prototype of about 8 lines in `Views`: 400 probes replay in 0.09 s (1.54 s with fix A alone), printing no error lines. 1,000 probes replay in 0.30 s and pass the 512 limit, since one rebuild holds only the starting view's blocks besides the new ones.
    - An edit's own refusals still stop a script at their line.
    - What changes: a schedule error is reported once, for the graph the script leaves, naming its node but not the line that caused it. A failed rebuild surfaces at the next frame.
