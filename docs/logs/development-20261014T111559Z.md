**Done**: the check against the principles, and a proposal.

- **It conflicts today with three rules.** V11: "Two recipes share only the contract on the connection between them". RV05: "Contracts are the only files that more than one node includes". RV06: "Code lives only in parts". RV00 holds, since shared code is no recipe. It serves C02, C04, C06 and GLSL01, but V11 is the higher section, so V11 wins until it changes.
- **Header only, no `.cpp`.** Native C++ already settled this as rule 5, "nodes share headers, not source files" ([native C++](../plans/native-cpp.md#the-runtime-boundary), decision 4). Each folder's C++ builds as one module (RV08), so a shared `.cpp` would need the build to find which modules use it, and a release build would link it once a view.
- **A small class or functions, not an operator.** It has no `bind` or `cook`, reaches no port and registers no command. The part keeps it as a member and hands it each event and Rect. So the part still decides in what order events count, as when a press on a scroll bar must not also move the caret, and every action still goes through the part's commands (V06).
- **Where:** `shared/` beside `contracts/`, at the top of the library and of a view. A C++ header opens `namespace VP_VIEW`, as a C++ contract does, so two views' copies stay two types in one release binary.
- **A drop copies the shared files a recipe includes** into the view's `shared/`, as it copies contracts. A file the view has already stays as it is, so a sync never updates one, as with contracts ([nodes and folders](../plans/nodes-and-folders.md#open)).
- **The mechanism, about 25 lines:**
  - `nodes.cmake`, `Manifest.cpp` (`unnamed_below`) and `Edits.cpp` (`Edits::add`) treat `shared/` as they treat `contracts/`: no node folder, and no node of that name;
  - `Library.cpp` copies `#include "shared/…"` as it copies `#include "contracts/…"`, and reads the copied shared files for their own includes, since `Scroll.h` includes `contracts/Rect.h`;
  - the include-map gate lets node code include `shared/`; the code-rules gate holds its headers to `namespace VP_VIEW`.
  - The include path and the live build need nothing: `-I<root>` already finds it, and a changed header rebuilds every module that includes it.
- **The first three headers:**
  - `Scroll.h`, for the editor, the terminal and later lists: the first row shown with its fraction, so a touchpad's small turns add up; the wheel; following a row, as the caret; the thumb's Rect; and a drag on it.
  - `PanZoom.h`, for the graph and the Perform panel: pan and zoom, the wheel zooming about the pointer, a drag moving, and the mapping to the screen. The graph keeps them in its `.ini`; the panel does not (3b).
  - `Words.h`, for the editor and the terminal: the run a double click selects, letters, digits and `_`, or a run of blanks, or one other character.

**Proposed text, for the lead to approve (A00)**, as its own commit before any code (A05):

- **V11** becomes: "In the library, a bigger recipe uses smaller ones and connects them; it never copies their code, or uses a bigger one and removes nodes. Two recipes share only the contract on the connection between them, a GLSL struct for data on the GPU or a C++ header for data between C++ nodes, and shared code: a header for a job too small to be a node, which each part that needs it includes. So every recipe stays whole on its own, any recipe that honors the same contracts can replace it, and a fix to a part or to shared code reaches every library recipe built on it."
- **RV05** becomes: "Recipes share only contracts and shared code. A contract is a GLSL struct in the `contracts/` folder at the top of the library or of a view, for the data one connection carries, and C++ reads it by reflection (RA03). A contract may also be a C++ header there, for the type a connection between C++ nodes carries. Shared code is a header in the `shared/` folder beside it, for a job too small to be a node: the part that includes it hands it what it needs, and it reaches no port and registers no command itself. Contracts and shared code are the only files that more than one node includes, and dropping a recipe copies those it includes into the view's `contracts/` and `shared/` (V03)."
- **RV06** begins: "Code lives only in parts and in shared code (RV05)." The rest stays.
