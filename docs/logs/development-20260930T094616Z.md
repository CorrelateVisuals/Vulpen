**Done** (baseline, before any IDE code)
- **Tests today.** ctest runs three tests: no arguments, `wave` for 120 frames, and `triangle` for 120 frames. Each checks only the exit code. A validation message does not fail a run, because no debug messenger is installed. The only gate is the include map.
- **Sanitizers.** ASan, UBSan and LSan in a debug build.
  - Headless `wave` on lavapipe is clean.
  - Every other leak report is inside libraries: the Wayland decoration plugin's GTK (fontconfig, pango), D-Bus, the Vulkan loader and the NVIDIA driver. None of them was allocated by our code. There is no UB report.
  - The POC's `lsan.supp` suppressed `create_instance`, which is our own function name. Suppressing by library does not hide our code.
- **Determinism.** `wave`'s readback is bit-identical run to run, and between debug and release, on NVIDIA. NVIDIA and lavapipe differ in 31 of 32 values, by up to 261 ULP (3.9e-6), because each driver implements `sin` to its own precision. So C01 holds bit for bit per device and driver, and a golden shared across drivers needs a tolerance. This is a tension with GLSL02's "every GPU gives the same result", for the lead.
- **Soak.** `wave` (release, unpaced, 120 s): memory flat at 184,732 KB, 8 threads, 34 file descriptors. `triangle` (60 s): +128 KB once, then flat; GPU memory flat at 50 MiB.
- **Signals.** SIGINT and SIGTERM end vulpen at once, and no destructor runs; there is no clean shutdown.
- **Swap stress.** 60 swaps, alternating a shader and a module. Memory +312 KB, then flat, then −204 KB: no leak trend. The mapped `recipe.so` count stays constant, so unloading works. No validation message.
- **Synchronization validation.** Layer 1.3.275 switches it on only through `vk_layer_settings.txt` (`VK_LAYER_SETTINGS_PATH`). With it on, removing the engine's compute barrier gave no report. It does not track accesses through buffer device addresses, so the buffer barriers V10 has the engine place need a test of their own.
- **GPU-assisted validation** caught an injected out-of-bounds read through a buffer address: 30 reports. Clean runs of `wave` and `triangle` report nothing. It is the check for GLSL02's out-of-range indices.
- **Fail loud.** Six broken manifests exit 1, each naming its mistake: an unknown word, a param nothing reads, a missing recipe, a cycle, an old version and a bad number. So do a truncated and an empty `.spv`, followed by a few errors that follow from them.
- **Working directory (RP02).** Running from `/tmp` works.
- **Heap on the hot path (CPP10).** Our code allocates nothing per frame: 64 main-thread allocations over a run, all at startup, in log lines or at shutdown. The process as a whole allocates about 4 times a frame headless and about 23 in a window. Those are in libraries: the driver, the loader and validation, Wayland's keyboard handling, GLib and D-Bus.
- **Thread races.** GCC 13's TSan needs `setarch -R` here, since it clashes with the kernel's address randomization. On lavapipe, 6 swaps are clean; on NVIDIA, it crashes inside the driver.
- **Scale.** 1,000 `wave` nodes run 300 frames in 0.22 s (0.7 ms a frame), at 162 MB maximum memory.
  - Loading 1,000 unconnected nodes and running one frame takes 0.26 s, the same as 10 nodes.
  - A chain, where each node reads the one before, takes 0.68 s at 1,000 nodes and 2.16 s at 2,000. Ordering grows faster than the graph (`Schedule::order`), and every edit will rerun it (IDE plan, row B2).
- **A hard limit fails without naming its cause (A02).** Past 1,024 nodes with a pass block, the load fails with `vkAllocateDescriptorSets failed: VkResult -1000069000`. The pool is sized by `max_passes = 1024` in `Pipelines.cpp`.
- **Duplicates parse and are then ignored (A02).** The loader accepts:
  - a param given twice, even with different values, and uses one of them;
  - a connection endpoint given twice;
  - two `[connection]` sections with the same name;
  - `[manifest]` twice, and `version` twice.

  A second `shader` is refused.
- **Manifest fuzz.** 300 mutated manifests in 15 s, with ASan, UBSan and LSan on lavapipe. 272 were refused with a named error and 28 ran. There was no sanitizer report, crash, hang or failure without a named cause.
- **Time in a float drifts (A03).** `Wave.cpp` adds `_speed` to a `float` every frame and never wraps it. At 60 fps, the wave runs 2.3% slow after 1.9 hours, 17% fast after 15.5, 22% slow after 28, 56% fast after 67, and stops moving after 4.4 days; unpaced, sooner. So the proposed frame block (IDE plan, row A1) cannot hold time as an accumulating `float`, and a 32-bit frame index there would wrap after 2.3 years at 60 fps.
- **No mutable globals (C13), checkable from the build.** Listing writable data (`.data`, `.bss`, not `.data.rel.ro`) in the built objects finds none in our code. It finds one in vendored VMA (`VmaBufferImageUsage::UNKNOWN`). A gate can run this at every build.
- **Library bounds assertions.** `-D_GLIBCXX_ASSERTIONS` with `-fstack-protector-strong`: `wave` and `triangle` run clean.
- **Fused multiply-add (C01, RC06, C10).** In C++ mode, GCC fuses `a*b+c` into one instruction at `-O2` whenever the CPU has FMA (checked with `-march=haswell`). The build sets no `-march`, so today's x86-64 builds have no FMA and stay bit-identical. On ARM64, which always has FMA (Raspberry Pi and some others), release would differ from debug and from x86. `-ffp-contract=off` prevents it.
