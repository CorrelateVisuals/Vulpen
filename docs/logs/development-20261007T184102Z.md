# Handoff — development — 2026-10-07T18:41Z

**Working on**: step 20 of the [IDE port](../plans/ide-port.md#order), `keys`, the theme and the keymap (E10, G3). Before building, the lead was asked who holds the focus and how a part knows it has it.

**Decisions** (the lead, 2026-10-07):
- **A: the `keys` part holds the focus.** No engine change (V05).
  - `keys` registers `focus <node>` and remembers the node in focus.
  - Each frame it turns keymap chords into commands, and hands the other keys and text, with the name of the node in focus, on one connection.
  - A part that takes keys reads that connection, not the raw input, and acts only when the name is its own.
  - The app's manifest sets where the focus starts.
  - Like input, a focus change stays out of the log.
  - Not chosen: B, the engine holds the focus and gives keys only to that node. It puts a UI idea in the engine, and chords would still need to reach `keys` first.
- **1, yes: a press inside a part gives it the focus.** The part sends `focus <its own name>` itself, since it knows its area and reads the pointer.
- **2, yes: the caret shows only in the part in focus**, so you can see where typing goes.
