- **A, the quit guard.**
  - Found:
    - `quit` is the engine's (`Commands.cpp`).
    - The close button ends the loop directly (`Runtime.cpp`, when `Window::poll` returns false).
    - `escape` reaches `quit` through modes.
    - Only the editor knows about unsaved changes (`Document::changed` in `Text.cpp`), so no guard can work without a general port (V05).
  - Design: engine, about 25 lines.
    - `Cook::hold(what)` in `runtime/Operator.h`. A node that would lose work if the run ended calls it each frame, naming what. Commands keeps this frame's holds and the frame before's, swapped in `Commands::frame()`.
    - `quit` refuses while either list holds anything. It names each, and says that `quit force` ends the run anyway. `quit force` is a second engine command.
    - The close button becomes a `quit` sent through the port. `Window::poll` returns false when a close was asked since the last poll, and clears GLFW's flag, so a refused quit leaves the window open.
  - Recipe side: the editor holds once a frame while a file has changes. It names the files, and says that `write` saves the file shown and `discard` drops it, as its `close` refusal does.
  - Test: the `ide` test's editor run types one more character after its write, then escapes until modes sends `quit`. Checks:
    - the run must still run all its frames;
    - it must print the refusal;
    - the file must hold only what was written.
    - This guards against silent data loss, and adds no run.
  - Known edge: a `write` and a `quit` in the same frame, as a pasted pair of lines or a sourced script, may be refused once, since the frame before still held. That errs on the safe side.
  - Docs: usage sections 7 and 12, the help texts, `Operator.h`.
- **B, folder completion.**
  - Found: Commands.cpp declares the `file` kind ("the folders and files where the path resolves"). But `complete` answers `<file>` with the placeholder itself (`names()` in `CommandLine.cpp`), so nothing is typed.
  - Design: recipes only, the command-line part.
    - `names()` takes the word begun. For `<file>` it lists the folder that word names, through `call.files().list`.
    - It resolves the folder from where vulpen started, `current_path() / folder`. That is how `Commands::resolved` resolves a typed line, and what the prompt counts from.
    - Hidden entries show only once the name begun starts with `.`, as in a shell. A name with a blank is left out, since it would split into two words.
    - Tab: a single candidate ending in `/` gets no blank after it.
    - The list shows each candidate from after the last `/` of the word typed. So Tab on `src/examples/` lists `triangle/` and `wave/`.
    - `view load` already takes a trailing `/` (`host()` in `Library.cpp`).
    - Also in `names()`, for D:
      - `[<node>]` and `<node>...` read as `<node>`, which `info [<node>]` and `select [<node>...]` need;
      - a `...` usage's last placeholder repeats, so `select a b<tab>` completes.
  - A folder that cannot be listed, as a file followed by `/`, is refused by the file port, naming why. The terminal shows that in red on Tab (A02) rather than hiding it.

- **D, selection in the graph.**
  - Found:
    - `node remove` refuses a node that a connection names or that holds a node. So a delete key that only sent it would fail on almost every node.
    - A C++ input that nothing connects is a load error (`Binder.cpp`). The CLI has `inspect` without a graph, so `inspect` cannot read the selection through a connection unless the CLI connects one.
    - The graph takes no keys today: it is not in the keys part's `typed` connection.
  - Design: recipes only, and the `ide` manifest gains one `to`.
    - **Commands.** The graph owns the selection: node names, with the hosted view they belong to. It registers three commands, so scripts and agents select as a click does (V06):
      - `select [<node>...]` selects those nodes, or with none, none;
      - `selected` lists them, a line each;
      - `delete` removes them.
      - Each acts only when the line addresses the view the graph shows, the newest hosted one, found from `call.view("")`. So a script's `select` works before the first frame.
    - **Presses** send `select`:
      - on a box not selected, `select <it>`;
      - on a selected box, the selection stays, so a drag moves every selected box. Let go without moving, only that box stays selected;
      - shift with a press adds a box or takes it out;
      - on the ground, the selection goes, unless shift is held; the graph then moves as now.
      - A press on a file row also opens that file. A press on the name row now only selects; before, it opened the node's first file.
    - **Look.** A selected box draws its border in `accent`, 2 pixels wide.
    - **Keys.** The graph takes the focus on a press in its area, as the editor and the terminal do. The `ide` connects `ide.keys.typed` to `ide.graph.graph.typed`.
      - `delete` or `backspace` sends `delete`.
      - `escape` drops the selection, then the focus, as elsewhere.
    - **What `delete` does.** It takes the nodes selected and every node inside them, deepest first.
      - A connection whose writer goes is disconnected.
      - One whose readers go is disconnected and connected again with the readers that stay.
      - Then each node is removed.
      - It is one command, so the log keeps one group, which a later undo takes back in one step (V08).
      - The folders stay, as with `node remove`. The removed nodes' boxes leave the graph's `.ini`.
    - **`info`.** `inspect`'s `info` becomes `info [<node>]`.
      - With no node it sends `selected`, and shows each node under its manifest header, `[node "<name>"]`.
      - Where no command `selected` is registered, as in the CLI, or nothing is selected, it refuses, naming `info <node>`.
  - Test: the `ide` test's graph run selects with presses and shift, types `info`, and deletes with the key, so asan and validation run the new paths. Its comment "its first file opens" changes, since that press now selects.

**Decisions for the lead (A00)**, from the designs above, in plain words. Each is built as recommended unless you say otherwise.
1. **The engine gains a hold (A).** Any node can keep `quit` from ending the run, naming what would be lost; the editor is the first. It is a new function on the frame's interface (`Cook`), with no new module or include.
   - Other way: the close button and `escape` ask, but a typed `quit` does not. That leaves the command scripts and agents use unguarded.
   - Recommended: yes.
2. **`quit force` ends the run anyway (A).** Without it, a run with unsaved changes ends only after `write` or `discard` on each file. Recommended: yes.
3. **In perform mode the refusal is out of sight (A).** The terminal is hidden there, so the close button seems to do nothing.
   - Other way: a refused quit goes back to edit mode, about 3 lines in modes.
   - Recommended: decide after trying it.
4. **The app id is `vulpen` (C).** The dock and the window list group windows by it. Recommended: keep.
5. **A press on a box's name row only selects (D).** Before, it opened the node's first file. A press on that file's row still does. Recommended: yes.
6. **Delete takes the connections and the nodes inside along (D),** as node editors do. `node remove` itself stays strict (A02).
   - Saying no: the key refuses most nodes, naming the connection.
   - Recommended: yes.
7. **The graph takes the focus on a press (D).** After a press in the graph, a press in the terminal is needed before typing there. Without it, the delete key in the editor would also delete the selected nodes. Recommended: yes.
8. **Selecting is three commands (D):** `select`, `selected` and `delete`.
   - So a script or an agent selects, asks and deletes as a click does (V06), and `info` reads the selection through the command port.
   - Other way: a connection carries the selection. That needs a new contract, and the CLI, which has no graph, would have to connect it.
   - Recommended: commands.
