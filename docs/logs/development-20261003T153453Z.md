**Decisions for the lead (A00)**, each built:
1. **`recipe new draw <name>` and `recipe new dispatch <name>`** replace the plan's `recipe new <name> <kind>`. The kind is a word of the command, so `complete` and `help` show both, and the engine needs no placeholder kind for it.
2. **Typed relative paths still resolve from where vulpen started**, which matches the folder the prompt shows. The other way is shell-like: they resolve from the current project, as after a `cd`.
3. **The frame block lives in `Pipelines`**, one for the process, rather than one per view.
4. **The frame block's precision.** `time` is a float, so it steps coarser than a frame after about three days (73 hours); `index` is a uint, so it wraps after 2^32 frames, about 2.3 years at 60 a second. Both follow the plan's layout. A shader meant to run for days should take its phase from `index`.

**Step 13 needs the lead first** ([ide-port decisions](../plans/ide-port.md#decisions-this-needs-a00)):
- **Operator ends of a connection** ([D5 in migration and implementation](../architecture/migration-and-implementation.md#open-decisions)), for A2 and A3. It decides whether one node's C++ can hand data, such as a list of rectangles, to another node's C++ over a connection, as shaders already do. The engine would keep the data where both ends can reach it, and move it between CPU and GPU only where one side is C++ and the other a shader. The other way, from the POC, is a port per kind of data, which grows the engine with every feature (V05).
- **The manifest word `instance_count`** (V04), for A4: how many copies a draw makes, a number or a port whose buffer's length sets it each frame. `invocations` then counts the vertices of one copy.
