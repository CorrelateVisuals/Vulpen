**The lead's direction, 2026-10-03**
- Fourth round: recipes had drifted. A drop had become a live `[deploy]` whose nodes took only param edits, which breaks V02. A recipe saves a view's nodes, a part of them, or one node, to drop into another view and change there as if built by hand. No `recipes/` folder for a view's own nodes, and no `recipe =` on each. The library holds building blocks; examples are apps built from them. One manifest per view.
- Fifth round: a drop is one command, a copy you may edit, which syncs while nothing changed; nesting shows in the manifest; child views as `[view "name"]`; `vertex_count`, `node new draw|dispatch` and `VP_OPERATORS`.
- Sixth round: "view stats like set param and connectors should keep working if unchanged externals"; "every node is a nested node, so every folder is a node basically. drop the word nested. list all files. and a new file is automatically part through it's location"; shared C++ headers in `contracts/`: agreed. "Start reformation on current code base … Make sure we leave no loose ends."

**Decisions for the lead (A00)**: the seven at [where the build differs](../plans/nodes-and-folders.md#where-the-build-differs-from-the-proposal). In short:
1. `shader` is gone: a node's shaders are its files by extension.
2. No node runs another's code.
3. Data folders are nodes too; a folder no node names is a warning.
4. A sync lets go of a param the library let go, naming it.
5. `node add` takes no words, for a group.
6. `child remove` reaches the host.
7. Renames past the decided ones (`Modules`, `nodes.cmake`, `module.so`).
