**Proposals for step 10** (not built):
- **B7, the file port.** `node.file(path)` in `bind` returns a `File`, and a relative path names a file in the node's recipe folder (RP02); `frame.files().text(file)` reads it again once it changed on disk (the watch), and `frame.files().save(file, text)` goes through `Files::save` (RA04). A node's files go with it, as its commands do, and `Ports` shares a file opened twice, so a rebuild's reopen costs nothing and the set stays bounded (A03). Opening only in `bind` keeps that bound; the template's `node.files().open(…)` would let `cook` open files no rebuild closes. It needs two choices: an edge `Schedule.cpp` → `Ports.h` (as 1 above), and each unfolded node knowing its recipe's source folder, best as a field `Manifest::flatten` fills and a save leaves out, as `where` is. The `library` part (E18) needs a folder listing and a copy too, for `recipe list` and `recipe drop`.
- **C3, hosted views.** `child add <name> <file>`, `child remove <name>`, `child list`, as the [CLI examples' log](../plans/cli-examples.md#the-log) shows: hosting is a primitive, so the log keeps it (V08). `Views` holds each child's view, unfolded view and schedule on the shared engine; each frame cooks the host, then the children in the order added, and runs all their passes. A line `<name>: <command>` reaches the child: `Commands::run` splits the name off, and `ViewLookup::find` and `replace` already take one. The command-line part keeps a current child, set by `view new` and `view load`, and adds the name to every typed line, so each log line stands alone. The live scan watches every child's root. Two children with one folder name are refused, since the build tree mirrors views by that name. A view outside `src/examples/` and the library is not built, so `view new` should create views there until the build learns of hosted views.
