- **B5, recipe commands** (step 6):
  - `Bind::command(usage, help)` registers a command the node answers in its `command` hook, as the [template](../plans/cli-examples.md#the-files) shows it. A refusal (no help, a bad usage, a name taken) becomes one of the node's errors, and the operator gets a handle that matches no run, as every other `Bind` call does.
  - **A node's commands last while it runs.** A rebuild removes the old schedule's commands before it binds, so each node registers its own again, and a node that went leaves none behind to block the name. A module swap removes them with the operators it drops, and a node left out with errors, or whose cook throws, removes them too. So the port never holds a handler in a module that is gone, which would be a use after free with no other sign.
  - `Commands::remove`, and ids from a counter, so removing one command never moves another's id.
  - **A name is one command**, as for the engine's: a second node registering it is refused, naming the node and the command. Two nodes of a part with commands cannot share a view then. The first app that needs that is the IDE's four panels at step 19 (D10); addressing a node's command by the node would land then.
  - `Call::reply` and `send` from the template are not built: their first user is the command-line part at step 8, and where a reply goes depends on the terminal port.
